====================================================================
PROJECT CONTEXT
====================================================================
Genealogical research database project (JewishGen URD Dev, NocoDB base,
base_id prsjtz30iuhk88f). Goal: build an ML/LLM classifier that predicts the
`doc_type` field (multi-label) for archival document metadata records.

doc_type labels in active use: V, C, L, O, P
  V = Vital record (birth, death, marriage, ...)
  C = Census document
  L = List of names such as refugees, pogrom victims, passengers, etc.
  O = Other type of document
  P = Passport applications and related documents
  M = legacy/undocumented value, excluded from scoring and prediction.

Key NocoDB tables:
  ML Document Set   mjrd3mg993pdtba  - frozen snapshot used for all ML work
  Schema Values      m3qkh46x5mvfgq0  - authoritative label definitions

Architectural constraints (still governing, not to be violated):
  - Do not modify the live Documents/Pages tables.
  - ML Document Set must stay a frozen, isolated snapshot.
  - Never use the `comments` field as a classifier input feature — it's added
    by the triager AFTER classification and would leak the answer.

====================================================================
DATA SPLIT DESIGN (three-way)
====================================================================
  train      - source for few-shot / fine-tuning examples
  validation - fond-disjoint holdout within seen archives; SAFE to reuse
               repeatedly during iterative prompt/model development
  test       - entire archives held out completely; meant to be touched
               ONCE for final reporting, not used during iteration

Split method: user-authored greedy algorithm. Root-level (archive) greedy
split produces train/test (~90/10, minimizing marginal doc_type distribution
difference via best-of-n random restarts). A second fond-level greedy split
carves validation out of the train pool — this converges less well (much
larger search space) and produces a real train/validation L-label imbalance
(21.5% vs 10.4%) that has been confirmed as a genuine property of the split,
not a data bug. Not yet remedied (open item, see below).

100%-test archives (zero train/validation representation) — CONFIRMED, do
not pull few-shot or "validation" records from these; they only exist in test:
  AGAD (14/14), DAPO (4338/4338), ДАХмО_Картотека (49/49), TSDIAL (131/131)

KEY MISTAKE FOUND AND FIXED THIS SESSION
====================================================================
All eval runs prior to this session (5-shot and 7-shot) drew their 46
test_cases via `ml_split=eq,test` instead of `ml_split=eq,validation` —
violating the project's own train/validation/test design and burning the
"touch once" test budget on iterative prompt development. Several of those
46 records came from 100%-test archives (DAPO, TSDIAL, AGAD).

FIXED: `/Users/jbrandt/code/ollama/eval_data.json` was rebuilt from scratch
with:
  - few_shot: 20 examples, all sourced via (ml_split,eq,train) filter
  - test_cases: 47 examples, all sourced via (ml_split,eq,validation) filter
Verified via bash: no duplicate test_case ids, zero exact-record-label
overlap between few_shot and test_cases, no AGAD/DAPO/TSDIAL/ДАХмО_Картотека
records present. Archive-name overlap between the two sets (e.g. both contain
CDIAK, DADNO, TSDAVO, DAKO records) is fine and expected — ml_split, not
archive identity, is what guarantees disjointness, since those archives have
records split across both train and validation.

Label balance achieved:
  few_shot (20):  V=1, C=8, L=8, O=9, P=5   (counts sum >20 due to multi-label)
  test_cases (47): V=10, O=15, L=11, C=11, P=10

Rationale for few-shot distribution: V is already easy/reliable, doesn't need
many examples. C, L, O, P are the confused labels from prior eval rounds, so
they're oversampled, including several multi-label combo examples (O+C, O+L,
O+L+C, O+C+P, O+L+P) to teach realistic co-occurrence patterns.

2. run_eval.py
   Self-contained Python 3 (stdlib only) batch eval script against a local
   Ollama instance.
   Usage: python3 run_eval.py --model qwen2.5:14b
          (defaults: --host http://localhost:11434 --data eval_data.json
           --out results.csv)
   Builds a fixed system+few-shot prefix (identical every call, enables
   Ollama's automatic prefix/KV-cache reuse) + one varying user turn per test
   record. Parses predicted doc_type letters via regex, scores against
   ground truth: per-label precision/recall/F1, overall exact-match
   (set-equality) accuracy, average Jaccard similarity. Writes results.csv
   with per-record detail and prints a summary table to stdout.
   VALID_LABELS = ["V","C","L","O","P"] (M excluded).
   No changes needed to this script for the 20-shot/validation-sourced
   update — it just reads whatever is in eval_data.json.
